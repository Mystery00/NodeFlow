# 帖子列表置顶标记设计

## 背景与调查

NodeFlow 的主题列表只展示节点、作者、时间和回复数，`Topic` 领域模型也没有置顶状态，因此即使 V2EX 列表单元携带置顶标记，解析后也会丢失。

本次同时检查了当前 V2EX `/recent`、节点页 HTML、公开旧 API、`D:/StudioProjects/v2er-fork` 以及多个开源客户端。公开 JSON API没有置顶字段，v2er 只实现了主题详情中的付费置顶写操作，没有列表状态实现。

模拟器实时验证定位到主题 `1233054`：它显示为 5 天前，却排在后续 1 小时内主题之前；对应列表 HTML 没有 `sticky`、`pinned` 或“置顶”文本，而公开 API 的 `last_touched` 已被服务端推进到当天。由此确认 V2EX 当前模板主要通过“把主题移动到时间倒序列表前部”表达置顶，客户端必须在保留显式标记兼容的同时识别列表头部的时间顺序反转。

## 目标

- 解析 V2EX 主题列表单元中的显式置顶标记，并保存在领域模型与 Room 缓存中。
- 首页、节点详情和其他复用 `TopicListItem` 的列表统一展示“置顶”标记。
- 标记视觉规格与节点 Chip 一致，但不响应点击，也不暴露按钮语义。
- 没有服务端显式标记时，仅依据列表显示时间相对正常倒序的异常位置识别置顶；不因首条位置或推广节点本身猜测。

## 非目标

- 不新增付费置顶主题的写操作。
- 不修改主题排序，不把推广节点等同于置顶。
- 不为确认置顶状态额外请求主题详情或公开 JSON API。

## 状态来源与解析

`V2exHtmlParser.parseTopicCell` 在列表单元出现以下显式信号时设置 `Topic.isPinned = true`：

- 单元或子元素的 class 名明确包含独立的 `sticky` 或 `pinned` 标识；
- 单元存在 `data-sticky` 或 `data-pinned` 且值为 `1`、`true`；
- 单元中的状态标签文本为“置顶”或 `pinned`。

完成单元解析后，Parser 以最近的 `.box` 主题列表容器分组，在各容器内分别计算最长显示时间倒序子序列，避免主列表与侧栏等无关区块互相污染。计算允许 60 秒误差，将不在该子序列中的最小异常集合视为服务端移动的置顶主题。这样既能识别排在列表首部或普通主题之后的旧置顶，也能识别插入后部的较新置顶，同时不会把被插入主题跨过的普通主题一并误标。显式置顶主题不参与倒序基线计算；缺少精确时间的主题不进行推断。正常列表不会产生标记，仅仅是第一条或推广节点也不会触发。

## 模型与缓存

`Topic` 新增默认值为 `false` 的 `isPinned` 字段，JSON 兜底数据因此保持非置顶。`TopicEntity` 同步新增非空布尔字段；数据库从版本 4 升级到 5，`MIGRATION_4_5` 使用默认值 `0` 增加列，保留已有主题缓存。Entity 双向映射必须保留状态。

Room schema 导出更新到 `app/schemas/.../5.json`，迁移测试验证旧数据保留且默认不是置顶。

## UI 设计

设计系统提供一个共用的紧凑标签视觉基座：

- `NodeChip` 继续使用可点击 `Surface`，行为不变；
- 新增不可点击的 `StatusChip`，复用相同高度、内边距、形状、颜色与文字样式；
- `TopicListItem` 在节点 Chip 前展示文案“置顶”的 `StatusChip`。
- “置顶”文案来自 string resource，便于统一维护和本地化。

元数据行现有间距规则继续生效。不可点击标记使用普通 `Surface`，不设置 `clickable`，因此不会抢占整行进入主题详情的点击，也不会被无障碍服务识别成按钮。

## 测试与验证

- Parser：显式中文标签、class/data 标记、列表头部时间反转、普通首条主题与推广节点不误判。
- Entity：`Topic ↔ TopicEntity` 映射保留置顶状态。
- Migration：4→5 保留旧主题并将 `isPinned` 初始化为 `false`。
- UI 内容：置顶主题返回“置顶”状态标签，普通主题不返回。
- 运行相关 JVM 测试、全部 `testDebugUnitTest`、`assembleDebug` 和 `lintDebug`。
- 在模拟器安装 Debug 包，通过受控的本地 HTML fixture 或测试预览验证标记视觉和不可点击语义；真实 V2EX 当前没有活动显式标记时，不伪造线上状态。
